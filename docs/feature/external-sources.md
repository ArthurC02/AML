# External Sources

> Modules: Extraction and Data Quality, Candidate and Identity Adjudication. Decided 2026-11-26 ([ADR-0012](../adr/0012-sources-and-web-information.md)): the three sources, their build order, and that the grounding search sends the customer's name forms (and only those). **Built** (source 2): `POST /api/pages`, `GET /api/pages/{pageId}`, the URL guard, the `FETCH_PAGE` job, the `web_page` record, the page problem codes, the page's publication date and the reading of a page's persons (page in, persons out); and the matching of a page's persons against a Case (`pageIds`, [below](#matched-against-the-customer)); each is marked *built* below. Everything else here (a stored source Profile with its versions, publisher and kind, risk categories from offences, grounding search, judgments, their APIs, codes, settings and records) is a specified proposal, not approved and not built.

Besides the Sanction / PEP list Profiles, the customer is matched against three external sources:

| # | Source | Starts from | Half ([operating architecture](system-overview.md#operating-architecture)) | Build order |
|---|---|---|---|---|
| 2 | a news page whose URL is received | the URL | Data Processing (the page); the Case links it | first |
| 3 | grounding search | the customer's name and keyword lists | Runtime Query (the query holds the customer's name) | second, on the page path of 2 |
| 1 | court judgments from the Judicial Yuan open data | a periodic fetch | Data Processing | last |

Each ends as source Profiles matched like a list Profile, so identity, source condition, [scoring rule](scoring-rule.md) and explanation do not change per source.

## Common path

```text
fetch ─► text ─► persons (attributes, events, stage; with location) ─► source document + source Profiles (namespace)
      ─► candidates for a Case ─► identity score ─► condition score ─► pair result ─► explanation [S#]
```

1. **Fetch** (*built*). `PoliteFetcher` ([web text](web-text.md#fetching)): robots.txt, the per-site delay, at most 5 redirects each checked against its own site's robots.txt, HTML and PDF only, 10 MB. Before every request, each robots.txt request and every redirect hop included, the **URL guard** (`Infra/Web/UrlGuard`, a trust boundary: the URL is someone else's input):
   - the URL is absolute `http` or `https`, holds no user name or password, uses port 80 or 443 and has at most 2,048 characters (`Core/Pages/PageUrl.Broken`);
   - every address the host resolves to is public, not just one: no loopback (127/8, `::1`), private (10/8, 172.16/12, 192.168/16), link-local (169.254/16, `fe80::/10`, `fec0::/10`), unique-local (`fc00::/7`), carrier-grade NAT (100.64/10), this-network (0/8), multicast, reserved (240/4) or unspecified (`::`) address, nor 192.0.0/24 or 198.18/15. An IPv4 address inside IPv6 (mapped `::ffff:`, NAT64 `64:ff9b::/96`, 6to4 `2002::/16`) is judged as that IPv4 address; Teredo (`2001::/32`), SIIT (`::ffff:0:0/96`), local-use NAT64 (`64:ff9b:1::/48`), the discard prefix (`100::/64`) and the IPv6 documentation prefixes (`2001:db8::/32`, `3fff::/20`) are refused. The IPv4 documentation ranges (192.0.2/24, 198.51.100/24, 203.0.113/24) count as public: they route nowhere, and the tests' stub site uses one. A host written as a number (`2130706433`, `0x7f000001`, `0177.0.0.1`, `127.1`, `[::ffff:a00:1]`) is the address it denotes. A bank whose internal hosts sit on public addresses needs those ranges added to `UrlGuard.IsPublic` (not built);
   - the production handler resolves the host again when it connects and connects only to those checked addresses, so a name that changes its answer between check and connect (DNS rebinding) is refused too. It uses no proxy, since a proxy would make the connect check see the proxy's address (a bank egress proxy needs its own rules, not built), and keeps no cookies.

   Known limit: one fetcher serves the host, and it fetches one request at a time (the per-site delay is kept by a single lock), so a slow site delays every other page. It keeps each host's robots.txt rules and last-request time in memory until restart; the hosts come from API callers, so that state grows by one small entry per distinct host, without a bound until restart. Ceiling: fine for a PoC's volume; a bounded cache and per-host locks are needed before the URL endpoint is open to many callers.

   The canonical URL is the page's key: lower-case scheme and host (an international name as punycode), no default port, no fragment, no `utm_*` parameter (`PageUrl.Canonical`). Every refusal is a page problem code ([below](#received-url-source-2)), never a silent null.
2. **Text** (*built*). HTML by `MainText` (title, main text, one line per block); PDF by `PdfText`, then `PdfText.Unwrap`. A site's repeated letterhead (`RepeatedLines`) is not stripped: a page is read alone, and that needs the site's other documents. A page with no main text is refused (`NO_MAIN_TEXT`; also a page nested too deep or not parsed in time), an unreadable PDF `PDF_REFUSED`. Persons are read from the main text only (not the title), and every offset is into the stored main text.

   **Publication date** (*built*, `Infra/Web/PublishedDates`, `publishedOn` and `publishedOnSource` on the page record). Read only where a page reliably states it, in this order: structured metadata (JSON-LD `datePublished`; `<meta>` `article:published_time`, `og:published_time` or `itemprop="datePublished"`; an element with `itemprop="datePublished"`; a `<time datetime>` outside a paragraph, list item, `aside`, `nav` or `footer`, since one in a sentence dates what the sentence tells and one in a list or sidebar another article), read before boilerplate is removed; then a publication label with its date in one short element of the page that holds nothing else, also outside the main text (a template's row `發布日期：`│`2026/9/8 下午 02:15:54`; labels 發布, 發佈, 發稿, 上版, 刊登 or 出刊 with 日期 or 時間), read before boilerplate is removed too, after the depth check; then, also for a PDF, a full date on a line of its own (`2026-11-20 10:30`, `2026年11月20日`, `民國115年11月20日`, `115年11月20日`, `發布日期：…`) or inside a dateline's bracket (`〔2026/11/20 記者／臺北報導〕`) among the first three lines of the main text, or such a label ending one of its first five lines (a PDF's letterhead runs into it: `…Press Release發稿日期：115年9月29日`; `新聞稿（115.9.10）`). After a label a 民國 year may also be written with dashes, slashes or dots (`115-11-20`, `115/11/20`, `115.9.10`) and a 12-hour time (`下午 02:15`) may follow. Not read as a label: one preceded by a CJK character, which makes it another label (`預定發布日期`, `原發布日期`, `附件發布日期`; on the measured pages and PDFs every real label starts its line or follows a space or Latin text); a label line longer than 200 characters; a label in a list, `aside`, `nav`, `footer`, `template` or `noscript`, or under an element whose class or id names boilerplate (`MainText`'s token rule: related, comment, footer …), inside a link, or on another article's card, however named: a label whose nearest block holding a heading holds only headings that are links (`<h3><a href>…</a></h3>`), since it dates another article (a card's date would otherwise become a report date). The labels skipped do not count toward the 20 looked at, and a page whose only publication labels are skipped states none, so its update date may stand in. On the 190 development documents the card rule changes no date read. A date in a sentence is not read. A matched date that is no day (day or month 0, month 13, 30 February) makes the date `MISSING`, never a coarser date, and so does a line or element holding both a publication and an update label (which date is which is not guessed). Dates are parsed by `PartialDate.Parse` as written (an ISO time's own local date), at their precision; a year after 民國 or of three digits is a 民國 year, four digits Western, and a bare two-digit year (`26年`) is not read. Every date found must agree at its precision; the most precise is kept, `publishedOnSource` `METADATA` or `TEXT` by where it came from.

   **Update date in its place** (*built*, decided by the user 2026-11-27). Only when the page states no publication date at all (every reader above found none; not when they disagree, when a value did not parse, or when a date was no day) does its update date stand in: an update label (`更新日期`, `更新時間`, `最後更新` with a colon) read in the same places, forms and skips as a publication label, or `<meta>` `article:modified_time`, `og:updated_time` or `dateModified`. The update dates must agree among themselves. It is kept with `publishedOnSource` `UPDATE_DATE` and the same bounds (after the fetch or before 1990: `MISSING`). Dublin Core `DC.Date` is not read at all. It is on 125 of the 128 development HTML pages: on the 103 that state only an update date it equals the article's 更新日期 on all 103; on the 22 that state a publication date it is the publication day on 9 and more than two years before it on 13 (every page of one template). An update date is shown, never a report date: a stated age on such a page is not compared ([step 6](#common-path)).

   `publishedOn` is null and `publishedOnSource` `MISSING` when none is found, when two disagree, when a value is present but does not parse (another format, a year after this one; the text is then not asked instead), or when the date is after the fetch or before 1990 (`PageReadings.Published`: after = later than the latest calendar date anywhere at the fetch instant, UTC+14; before 1990 is taken as misread, since it would shift every stated age). The page is untrusted: each of the first lines and each metadata value is cut to 200 characters (a JSON-LD block to 64K) before matching, and every pattern has a match timeout whose expiry is `MISSING`, never a failed page. The fetch time only bounds it; it never stands in for it. A page not read has neither. Measured on the real labelled development documents (190: 128 stored HTML pages from six site templates, 33 prosecutors' PDF releases, 29 judgments; counts only): a publication date on 55 (`TEXT`: HTML 22 of 128, every page with a publication label; PDF 33 of 33), an update date on 103 (`UPDATE_DATE`: one template that writes no publication label; on each the article's 更新日期, the first in page order, not the site footer's), `MISSING` on 32 (a template of 3 pages whose update label the reader does not reach, and the 29 judgments, whose date stands at their end and is the ruling's). Where a page states both (22), the labelled update date is the publication date's day on 20, 1 to 30 days later on 1, 31 days to a year later on 1, never earlier. The check is mechanical, not a person reading each page: a looser independent pattern (any date after a publication or update label anywhere in the page or text) and masked page shapes (labels and digit patterns, no words). Against it no date read disagrees, on the 190 and on a sample of 40 HTML pages stratified by template (17 publication dates, 20 update dates, 3 `MISSING`; 0 disagreeing, 95% interval 0 to 8.8%); "0 wrong" means no disagreement with that check. The 3 `MISSING` pages show an unlabelled date beside their title, not read.
3. **Persons** (*built*, `Core/Pages/PageReadings`). The rules of the [news digest](watchlist-and-adverse-information.md#news-digest), given no Profile names, read every person the text names (a name after a role, a name opening a clause, including the lead's first clause after a dateline's closing bracket 〔…報導〕, a dotted or pseudonymous name, a lettered party, the anonymised forms linked as the digest links them), not only one; when the news models are configured, each person they find whose mentions touch none of the rules' persons is a person too, marked `MODEL_READ` (the rules' own `RULE_READ`), with the forms where written, the model's party and no role word, its events left in the models' reading. A name in a place no rule reads (after 同案的, in a list without a role) is found only by the models; without them it is not read, never guessed. For every person, whoever found it: the forms written, each mention's offset and length, the roles and party, the identifiers next to a name (each with the offset of its text nearest a mention; an ID number masked), the stated age (`StatedAgeCheck`), the stated birth dates and gender (the digest's identifiers, parsed as `NewsStatedCheck` parses them), the person's events (those whose actor the digest names as them; the rest are the page's `otherEvents`) with their sentence's offset, and the legal stage by the person's forms through `LegalStageReading`, voted by `StageVote` with the stage models when configured, exactly as an attached text's ([three readers](watchlist-and-adverse-information.md#three-readers)). The news models, when configured, also add their whole reading (`model`), kept apart. A person's `readBy` says who found them; nothing decides on it here. In a Case it is the Profile finding `MODEL_READ` and the line in the explanation; nothing is decided on it there either ([below](#matched-against-the-customer)).
4. **Source document and source Profiles.** The page is one source document. *Built* (`web_page`): canonical URL, final URL, media type, title, fetch time, SHA-256 of the body, the main text, the publication date with its source (step 2) and the reading; each person read has the key `WEB:<pageId>-<n>`. *Built* in a Case: each person is a `SourceProfile` made when the Case is analysed (`PageCandidates.Profile`), not stored: its unmasked written names, the full name first, and the finding `MODEL_READ` when only the models found it; nothing else, since a page has no field beside the name (what is written next to it is stated, step 6). Proposed: publisher (the host's allowlist entry), kind (`JUDGMENT`, `PRESS_RELEASE`, `NEWS`), and a stored source Profile with citizenship, roles and the events as notes. Its key names the namespace (`ProfileKeys`: `IdOf` strips either built namespace, `IsWeb` tells a page person):

   | Namespace | Key | From |
   |---|---|---|
   | `DJ:` | the list vendor's Profile ID | list exports (built; a bare id is read as `DJ:`) |
   | `WEB:` | the page id (first 16 hex of SHA-256 of the canonical URL), `-`, person number in the document | a received URL (built) or a search result |
   | `JY:` | the judgment's id on the open-data platform, `-`, person number | a judgment |

   A new version of the same page (another text hash) is a new version of its persons; the version a Case revision used is pinned with the Case ([below](#matched-against-the-customer)).
5. **Candidates** (*built* for `SOURCE_PAGE`). A page person is a candidate for a Case when one of its unmasked written forms is EXACT against one of the screened subject's names by the identity pipeline's own name comparison (`NameComparison.CompareNames`, [name comparison](identity-adjudication.md#name-comparison)); a PARTIAL name or the reading key alone is no candidate, as a PARTIAL name is never a hit elsewhere. Retrieval mode `SOURCE_PAGE` (a received URL); `SOURCE_SEARCH` (search) and `INDEX_SEARCH` over the judgment index are proposed. Proposed: an anonymised form linked to no full name (王男, 王姓男子) a candidate as `PROFILE_SURNAME`, NAME `PARTIAL`, with the finding `SURNAME_ONLY`.
6. **Identity, condition, score** (*built* for a received page). `IdentityDecisionPolicy` compares the subject with the page person's Profile, the page's text given as its attached news with the page's publication date as its report date (`PageCandidates.News`; null when `MISSING` or `UPDATE_DATE`, never the fetch date), so the age, birth dates and gender written next to the name are stated values compared as attached news's are (`StatedAgeCheck`, `NewsStatedCheck`). A stated age is compared at the publication date (±2 years, `AGE_COMPATIBLE_AT_REPORT` or `AGE_DIFFERENCE_AT_REPORT`); on a page without one it is recorded and not compared (`AGE_NOT_COMPARABLE`). An update date standing in (`UPDATE_DATE`) is no report date, so the age is not compared either and can conclude nothing: on the 22 development pages that state a publication date, `DC.Date` lay more than two years before it on 13 and one labelled update date up to a year after it, and an update date later than publication makes a stated age look too young, toward `STATED_DOB_CONFLICT` for the same person. The labelled update dates alone were within a year on all 22 (20 the same day); they are not used either, since the 103 pages dated only by an update date come from a template on which the gap cannot be measured. As for attached news (user, 2026-11-27): when every comparable birth date and dated age the page states is more than two years from the customer's DOB, the pair is the validated hard conflict `STATED_DOB_CONFLICT`, NO_MATCH. Unlike attached news, a page's birth date within two years is neutral (`PAGE_BIRTH_DATE_WITHIN_TOLERANCE`), neither support nor a difference ([two-year conflict on stated values](identity-adjudication.md#two-year-conflict-on-stated-values)). The report date also serves the age at a dated role and the digest's dates, as for attached news, and the advisory [implausible age at a dated document](identity-adjudication.md#implausible-age-at-a-dated-document-advisory): a customer under 14 on the publication date of a page that names the person as an accused or a company officer is hinted (`AGE_IMPLAUSIBLE_AT_DOCUMENT`, REVIEW), never concluded; an update date never counts. The condition is ADVERSE_MEDIA with the stage the page reading voted; a person the rules read with a role word that is no suspect's raises none (`NOT_HIT`, [below](#matched-against-the-customer)). Risk categories from the offences are proposed. The [scoring rule](scoring-rule.md) takes the source kind of the record's and the text's values, measurement only.
7. **Explanation** (*built* for a received page). The page is `[S#]` with its URL, the host as publisher, the publication date when the page states one and the fetch date as retrieval time; a page dated only by its update date has no publication date there, and the external-data line says so with the date (`網頁未載發布日期，只載更新日期 … (UPDATE_DATE)，不作報導日期，所載年齡不比對`); the news digest of the page is given for the matched person; every item cites its sentence. Kind is proposed.

### One page, many persons

A page naming several people gives one source Profile per person. Only those whose names match the subject become hits of that Case; the others stay on the document (they may be another customer's hit) and are never assigned the matched person's events: an event belongs to the persons the sentence makes its actor or object, as in the news digest. Two mentions merge into one person only by the digest's rules (an anonymised form linked to exactly one full name); otherwise they stay apart.

### Same event

Reports of the same party, event time and charge are one event, whether they come from two pages, a page and a judgment, or a page and a list Profile's attached news. The event keeps every source; identity facts and the condition stated about it count once, at the most reliable source ([scoring rule](scoring-rule.md#identity-score)). Hits on different namespaces for the same person stay separate hits, linked by the shared event (`SAME_EVENT_AS`), so the Case hit count stays a count of Profiles.

### Redacted names

Published judgments mask names and addresses (王○明, ○○路, A男, 甲). *Built* for a received page: a written form with a masking character (○ ◯) is not compared, since the name key would drop the mark (王○明 read as 王明); a person with only masked forms is screened `PROFILE_MISSING` with `REDACTED_NAME` and is no candidate. Proposed with judgments: a masked name matching by its visible characters at the same positions and the same length, NAME `PARTIAL` with `REDACTED_NAME`, never EXACT. A fully masked name (A男, 甲) is no candidate. A masked ID number or address is shown and not compared.

### Licence and use

- Judgments and government press releases are outside copyright (著作權法 第 9 條); ordinary news is not ([web text](web-text.md#sources-whose-text-may-be-used)). For screening, a page is read and its text kept as the Case's evidence; quotes in the explanation are the cited sentences. A page is training text only when it is in web text's table.
- The open-data platform asks that a judgment it removes be deleted: a removed judgment's text and source Profiles are deleted from the source store, and later revisions no longer use it.

## Received URL (source 2)

Fetching is slow (robots.txt, a site's `Crawl-delay` up to a minute), so it is a job; screening against a page already read is synchronous, as `POST /api/cases` is today. A received URL counts as attached: it is exempt from the domain allowlist ([external lookups](security-and-privacy.md#external-lookups)), not from the URL checks of step 1.

```text
POST /api/pages                      fetchPage      tag Sources           built
GET  /api/pages/{pageId}?view=summary|full          getPage              built
POST /api/cases                      + pageIds      createCase (existing) built
POST /api/cases/{caseId}/analyses    + pageIds      reanalyzeCase        built
POST /api/batches                    items + pageIds submitBatch         built
```

- *Built.* `POST /api/pages` body `{ "url": "…" }`. A page whose stored outcome (`READ`, `REFUSED` or `FAILED`) was fetched within a day (`PageService.MaxAge`, a constant) returns `200` with its summary view. Otherwise `202`, `Location: /api/pages/{pageId}`, body `{ pageId, url, status: PENDING, jobId, batchId }`, and a `FETCH_PAGE` job, queued in the same transaction as the page (payload `{ pageId, url }`, no customer data; idempotency key `FETCH_PAGE:{pageId}:{UTC date}`, so a page is fetched at most once a day: a page already queued that day answers `202` with that job). `pageId` is the first 16 hex digits of the canonical URL's SHA-256; `url` is the canonical URL.
- *Built.* `GET /api/pages/{pageId}` returns `{ pageId, url, status, requestedAt, jobId, batchId, problem, finalUrl, mediaType, title, fetchedAt, contentHash, text, persons[], otherEvents[], model, publishedOn, publishedOnSource }`; `publishedOn` is a partial date at its precision, `publishedOnSource` `METADATA`, `TEXT`, `UPDATE_DATE` (the update date in place of an unstated publication date) or `MISSING` (both absent until the page is read), kept in the summary view; status `PENDING`, `READ`, `REFUSED` or `FAILED` (both with `problem`). Each person has `profileKey` (`WEB:<pageId>-<n>`), `name` and `forms`, `roles`, `party`, `mentions` (offset, length), `identifiers` (ID numbers masked, each with its offset), `statedAge`, `statedBirthDates`, `statedGender`, `stage` with `stageBasis`, `stageReaders` (when models vote) and `stageReasonCodes`, `events` (each with its sentence's offset), and `readBy` (`RULE_READ` or `MODEL_READ`, kept in the summary view). `view=summary` (default) leaves out the text, the identifiers, the stated values, the events, the readers (their quotes) and the models' reading, as the other summaries leave out all but names; `view=full` returns everything. `kind` and `publisher` are proposed with the source document.
- *Built.* Job: `FETCH_PAGE` retries a transient problem (HTTP 408, 429 or 5xx, `ROBOTS_UNAVAILABLE`, `UNREACHABLE`) under `Batch:MaxAttempts`, the problem code as the job's error code; the last attempt stores the page `FAILED` with it and the job succeeds. A permanent problem sets the page `REFUSED` at once and succeeds the job. A configured stage model's missing answer retries as an analysis does (`STAGE_NO_ANSWER`); the last attempt stores the reading with `STAGE_READER_NO_ANSWER`. A job dead-lettered on its last attempt by a timeout or an exception stores the page `FAILED` with the job's error code as the problem (`TIMEOUT`, `EXCEPTION:<type>`), so a page is not left `PENDING`; a job dead-lettered by its lease (`LEASE_EXPIRED`, a crashed host) leaves the page `PENDING` until it is submitted again on a later day or re-run. Only the job the page is queued under stores its outcome, so a late earlier job never overwrites a newer fetch. The job completes with no Case or revision.
- *Built.* Screening: `pageIds` (JSON array, or a repeated multipart field) sits beside `files`; see [matched against the customer](#matched-against-the-customer).

Errors, RFC 9457 as elsewhere ([errors](pipeline-api-and-batch.md#errors)):

| Code | Status | When | |
|---|---|---|---|
| `INVALID_REQUEST` | 400 | no URL, not absolute, not http(s), user info, a port other than 80 / 443, over 2,048 characters; `errors[]` gives `{ parameter: "url", rule }`; an unknown `view` | built |
| `NOT_FOUND` | 404 | an unknown page | built |
| `PAGE_NOT_READY` | 409 | `pageIds` names a page still `PENDING`; `errors[]` gives `{ parameter: "pageIds", pageId, status }`; fix: wait for `READ` | built |
| `PAGE_UNUSABLE` | 400 | `pageIds` names a page unknown (`status: NOT_FOUND`), `REFUSED` or `FAILED`; `errors[]` gives each page, its status and problem; checked before `PAGE_NOT_READY` | built |

### Matched against the customer

*Built.* A Case names pages by `pageIds` on `POST /api/cases`, `POST /api/cases/{caseId}/analyses` and each item of `POST /api/batches`; files stay required as without pages (`INPUT_INCOMPLETE`).

1. **Pinning.** `PageService.PinAsync` looks up each page id: a `READ` page becomes the input file `網頁_<pageId>.json` (the page record as read), merged with the uploaded files and stored with them in `case_input`, so it is the Case's input, in the Runtime Query half; the page record gains nothing of the Case. A batch pins its items' pages when it is submitted, and a page problem refuses the whole batch. `TxtCaseReader` reads the snapshot into `CaseInput.Pages` and its hash into the input hashes; the lineage lists each page with its text hash. A re-analysis of the stored input (as a changed list Profile queues) reads the pinned version; a page fetched again is used only when an analysis names it again.
2. **Screening.** Every person on every pinned page is compared by name (step 5) and recorded in the revision (`result.pages[].persons[]`: key, name, `readBy`, name status and detail, mode `SOURCE_PAGE`, `candidate`), candidate or not; none is dropped silently. A page with no candidate adds no hit.
3. **Hit.** Each candidate is a hit with `candidateRows` 0, its Profile from the page (step 4), the page's text as its attached news, identity by `IdentityDecisionPolicy`, the pair through the combination matrix, the disposition and the risk score as for any hit.
4. **Condition** (`SourceConditions.FromPage`, basis `PAGE_READING`): ADVERSE_MEDIA with the stage the page reading gave the person, voted then, not read again. `NOT_HIT` with `PAGE_PERSON_NOT_SUSPECT` when the rules read a victim's or an official's role word next to the name (被害人, 告訴人, 檢察官, 法官 …) and no suspect's (a suspect's word on any mention wins); the news models' party is not used for this, since a model's role is not measured. 證人 concludes nothing: a judgment cites a co-defendant's or an accomplice's testimony as 證人, so a witness is treated as any person with no role word. Otherwise `HIT` with the stage, or `UNKNOWN` when the stage is `UNKNOWN` (with `PAGE_STAGE_NOT_READ` when no stage code says why).
   Measured (real labelled development news, counts only, 2026-11-27): with 證人 counted as non-suspect, 9 of 311 labelled suspects or defendants (2.9%) were marked non-suspect, all exact-name matches, all by 證人, clustered in 3 judgments where a co-defendant testifies; none by a victim's or an official's word. Residual risk: a victim's word is weak in the same way where one person is the complainant in one count and a defendant in another (cross-complaints, 互告) and no suspect's word stands directly before any mention of the name; such a person is concluded `NOT_HIT`. The same holds for an official's word on a defendant written with that title (a former prosecutor or lawyer). Neither was observed in the 311; both are kept until measured otherwise. A witness's word ranks above an official's across a person's mentions, so a person written once as 證人 and once with an official's title is treated as a witness and is not concluded `NOT_HIT`. A page's missing stage-model answer (`STAGE_READER_NO_ANSWER`) stays on the condition and does not retry the Case: the page job already retried it.
5. **Explanation.** The hit's external-data line names the page person and says the page carries no birth date, citizenship or gender field beside what is written next to the name, and that the person was read by the news models when `MODEL_READ`.

Measured on the synthetic pages ([PoC delivery plan](../plan/poc-delivery-plan.md#received-url-matched-against-the-customer)).

A host that resolves to a non-public address is not refused by `POST`: the guard resolves names when it fetches, so it is the page problem `URL_NOT_ALLOWED` (the page `REFUSED`), for the URL received and for every redirect hop alike.

Page problems (`problem`, kind `PAGE_PROBLEM` in the code catalog; *built*): `URL_NOT_ALLOWED`, `ROBOTS_DISALLOWED`, `ROBOTS_UNAVAILABLE` (transient), `UNSUPPORTED_MEDIA_TYPE`, `TOO_LARGE`, `TOO_MANY_REDIRECTS`, `HTTP_STATUS:<n>` (transient for 408, 429 and 5xx), `NO_MAIN_TEXT`, `PDF_REFUSED` (unreadable, encrypted or over the limits), `UNREACHABLE` (no address, connection failed or timed out; transient).

## Grounding search (source 3)

The system searches for the customer itself ([ADR-0012](../adr/0012-sources-and-web-information.md), D1) and reads the pages found through the path of source 2.

- **Queries.** From the subject's names only: the name as written, its Traditional form, its romanizations (`Romanization`, at most two spellings), each quoted, combined with one fixed keyword list per query (for example offences: 詐欺, 洗錢, 貪污, 賄賂, 背信; procedure: 起訴, 判決, 通緝, 羈押, 地檢署). At most `Search:MaxQueries` (proposal 4) queries per subject and the first 10 results each, the bank specification's 「搜尋引擎結果前 10 筆」. Nothing else from the customer side goes into a query (no date of birth, identifier, address, phone, email, account, employer, `subjectRef` or Case id); a query that would hold a digit run of four or more is refused and recorded, not rewritten.
- **To be supplemented later.** Adding an employer, a city or another attribute to the queries, to narrow a common name, is a planned extension ([ADR-0012](../adr/0012-sources-and-web-information.md)): not built, and it needs its own decision on what leaves the bank.
- **Port.** `IWebSearch` in Core (`SearchAsync(query) → results[]` with rank, URL, title, snippet); one Infra implementation per provider, chosen by configuration, none built. The provider is [open](../plan/open-questions.md#external-sources): Google's Custom Search JSON API is closed to new customers and ends on 2027-01-01; Google points to Vertex AI Search (at most 50 named sites) or to a request form for full web search. Only the result list is used, never a generated answer.
- **Filtering.** Each result URL is canonicalised and kept only when its host is on the maintainer-managed allowlist (judicial and government sites, mainstream media; no forums, blogs, content farms, aggregators, wikis); results are de-duplicated by canonical URL, and a page already read within `PageService.MaxAge` (a day) is reused. Each kept result becomes a `FETCH_PAGE`; the snippet is never evidence.
- **API.** `POST /api/cases/{caseId}/searches` → `202` with a `SEARCH_WEB` job, which runs the queries, fetches the kept pages and then re-analyses the Case with them (`SOURCE_SEARCH`), a new revision; `GET /api/cases/{caseId}/searches/{searchId}` returns the queries, each result with its allowlist outcome and page status. A Case-level batch option follows the same job.
- **Record.** The `search_run` is stored with the Case: query texts, provider, time, results. General logs carry the search id only.

## Court judgments (source 1, outline)

- **Fetch.** The 司法院資料開放平臺 API and monthly archives need an account; a `SYNC_JUDGMENTS` job runs on a schedule (a scheduler only enqueues into the job table, [ADR-0010](../adr/0010-persistence-and-batch.md)).
- **Incremental sync.** A cursor per court and kind (the last period or change list read) is stored; each run reads what is new or changed since, and deletes what the platform has removed.
- **Store and index.** Each judgment is a source document of kind `JUDGMENT` with `JY:` source Profiles from its party lines (被告, with the age, birth date and residence the court states, masked as published) and its holding; the source Profiles enter the list index, so `INDEX_SEARCH` finds them by name inside the bank.
- **Open.** Re-screening existing customers when a new judgment arrives needs a customer-name index in the Runtime Query half; the account, schedule and scope are [open](../plan/open-questions.md#external-sources).
